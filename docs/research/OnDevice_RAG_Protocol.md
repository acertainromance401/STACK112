# 온디바이스 RAG 구현과 논문 평가 프로토콜

## 약어와 평가 조건

| 표기 | 의미·적용 범위 |
| --- | --- |
| RAG | Retrieval-Augmented Generation, 검색한 원문 근거를 생성 입력에 결합하는 검색 증강 생성 |
| LLM | Large Language Model, 대규모 언어모델. 이 프로토콜의 주 생성 모델은 Llama |
| B0 · `currentOnly` | 현재 판례 근거 E0만 사용하는 기준 조건. 참고 검색만 생략하며 원문은 제공 |
| B1 · `keyword` | 현재 판례 + 키워드·사건번호 검색 참고를 사용하는 비교 조건 |
| S · `semantic` | E5 코사인만으로 참고를 선택하는 후속 의미 검색 단독 조건. 키워드 점수·사건번호 가산·RRF 없음 |
| H · `hybrid` | Hybrid, 현재 판례 + 키워드·E5 의미 검색 순위 융합 참고를 사용하는 제안 조건 |
| B2 | 사용하지 않는 조건 표기. 기존 생성 파일럿은 B0/B1/H, 후속 검색 분해 실험은 B1/S/H로 구분 |
| E0 | Evidence 0, 현재 판례에서 선택한 근거 청크·실제 전달 발췌의 ID |
| E1 | Evidence 1, 첫 번째 참고 청크·실제 전달 발췌의 ID |
| E2 | Evidence 2, 두 번째 참고 청크·실제 전달 발췌의 ID. E1과 같은 판례에서 나올 수 있음 |
| E5 / RRF | multilingual-e5-base 검색 임베딩 모델 / Reciprocal Rank Fusion, 키워드·의미 검색의 역순위 융합 |
| L1 | 별도 3문서 파일럿의 첫 질문 ID: 재산분할 기여도·쌍방 사정의 참작 기준 |
| L2 | 같은 파일럿의 둘째 질문 ID: 97므1486을 명시한 공통 법리 비교 |
| L3 | 같은 파일럿의 셋째 질문 ID: 면접교섭 이행명령의 새 조건 부가. 기대 참고 없음 |
| P@3 | Precision at 3. 문서 ID 중복 제거 후 상위 최대 3문서에서 찾은 관련 문서 수 / 고정 분모 3 |
| R@3 / Recall@3 | Recall at 3. 같은 상위 문서에서 찾은 관련 문서 수 / 전체 관련 정답 문서 수 |
| MRR@3 | Mean Reciprocal Rank at 3. 같은 상위 문서에서 첫 관련 문서 순위 역수의 질문 평균 |
| L2 정규화 | 숫자 벡터의 유클리드 길이를 1로 맞추는 처리. 질문 ID L2가 아님 |
| GGUF / Q4_K_M·Q8_0 | 모델 저장 형식 / 가중치 양자화 방식 표기 |
| KV | Key·Value. 생성 엔진이 재사용하는 어텐션 캐시 정보 |
| p50 / p95 | 50·95백분위. 이 프로토콜은 정렬한 표본의 nearest-rank 방식 사용 |
| OCR / E2E | Optical Character Recognition, 이미지 문자 인식 / End-to-End, 정해진 시작부터 끝까지의 경로 검사 |
| JSON / ID | 데이터 교환 형식 / Identifier, 식별자. `queryID`는 질문, 문서 ID는 판례, 근거 ID는 실행 내 발췌를 가리킴 |

**E는 Evidence(근거)이며 임베딩 벡터가 아니다.** E5는 검색에 쓰는 숫자 벡터를 만들고, E0·E1·E2는 선택한 텍스트 근거에 붙이는 이름이다. 근거 ID는 실행마다 붙이고 참고 유무·예산에 따라 E1·E2가 빠질 수 있다. `[E0,E1]`은 두 근거를 인용한다는 표시이지 내용의 타당성을 보증하지 않는다.

L1~L3는 개별 평가 질문 번호다. 연구 목표를 뜻하는 RQ(Research Question)와 구분하며, 미실행 단일 판례의 `sc-q01`~`sc-q10`과도 다른 질문 집합이다. 정답 문서가 없는 질문의 Recall·MRR는 미측정으로 두고 ‘참고 없음 판정’을 따로 평가한다.

## 1. 범위와 주장 가능한 내용

STACK112 iOS 앱의 기존 학습 카드는 보존하고, 상세 화면에 별도의 **원문 근거 분석**과 **RAG 평가**를 추가했다. 서버와 외부 벡터 DB는 사용하지 않는다. 사용자 승인에 따라 빌드 준비 때 다국어 임베딩 GGUF를 한 번 받아 번들에 포함하며, 앱 실행 중 네트워크나 모델 다운로드는 없다. 기존 카드의 원문 우선 후처리를 새 경로의 생성 결과에 적용하지 않으므로 원시 생성 결과와 실패를 그대로 관찰할 수 있다.

논문에 사용할 수 있는 구현 설명:

> SwiftData에 저장한 판례 원문과 메타데이터를 기기 내에서 읽고, 원문 위치를 보존한 청크를 생성한다. 사건번호·키워드 검색과 multilingual-e5-base의 코사인 검색을 순위 융합한다. 임베딩은 GGUF Q8_0 인코더, SentencePiece 토크나이저, mean pooling, L2 정규화와 query/passage 접두사를 사용한다. 실제 생성 모델의 토큰 예산 안에서 근거 발췌를 구성하고 로컬 언어모델의 문장별 인용을 기초 검사한다. 검색 관련성, 근거성, 추론 시간, 메모리, 출력 성공을 분리해 기록한다.

**아직 주장할 수 없는 내용:**

- 실제 판례에서 검색 정확도·법률 정답률이 개선되었다는 결론.
- 실기기 지연·메모리·발열·배터리 측정 결과.
- 인용 ID 및 문자열 겹침 검사만으로 법률적 함의가 검증되었다는 주장.
- E5를 DPR 또는 이 프로젝트에서 별도 학습한 법률 특화 임베딩으로 표현하는 것.
- 작은 합성 평가셋의 결과를 실제 법률 자료 성능으로 일반화하는 것.
- 기존 카드·기존 OX 퀴즈가 새 연구 경로를 사용한다는 주장.

원문은 SwiftData에 영속 저장한다. 청크는 요청 시 원문에서 결정적으로 재구성하며, 별도 영속 벡터 인덱스는 만들지 않는다. 청크 식별자와 원문 해시는 재실행 간 원문이 같은지 추적하는 용도다.

검색 상위 청크는 3개, 문서당 최대 2개다. 생성에는 현재 판례의 질문 관련 청크를 E0으로, 참고 청크 최대 2개를 E1/E2로 전달한다. 예산이 작으면 참고 1개까지 줄이고 더 짧게 발췌한다. 출력에 보이는 근거는 **실제로 전달한 발췌**다. 참고가 있었는데 최소 참고도 보존할 수 없으면 명시적으로 실패한다.

### 검색 구성 분해와 비용 측정

- **B1:** 기존 키워드·사건번호 경로. 동작을 변경하지 않았다.
- **S:** 같은 후보·청킹·문서당 제한 아래 E5 코사인 0.30 초과 청크만 코사인 내림차순으로 선택한다. 키워드 경로를 실행하지 않고 사건번호 가산도 하지 않는다. 임베딩 전체를 사용할 수 없으면 명시적으로 실패하며 B1로 대체하지 않는다. 일부 청크만 의미 점수가 없으면 경고 후 제외한다.
- **H:** 기존 키워드 + E5 RRF 경로. 의미 검색 불가 시 기존처럼 경고와 `effectiveMode=keyword`를 기록한다. 그러한 실행은 H 측정으로 집계하지 않는다.

새 S는 분석·평가 화면에서 선택할 수 있지만 **기본 분석 모드 H와 기본 평가 선택 B0/B1/H는 유지**한다. 기존 9개 생성 파일럿의 반복 범위도 B0/B1/H로 고정해 새 모드를 과거 결과에 섞지 않는다.

후속 검색 전용 검사는 생성 LLM을 호출하지 않는다. 각 질문·검색 구성마다 provider를 새로 만들어 최초 검색을 1회 측정하고, 같은 provider의 문서 벡터를 유지한 채 질문 벡터만 제거한 뒤 3회 측정한다. 따라서 후자는 **문서 준비 후 새 질문 인코딩을 포함한 검색 비용**이지 완전히 캐시된 질문의 조회 비용이 아니다. 초기화 비용은 최초 검색에 포함되며 OS 파일 캐시는 초기화하지 않는다. 모드 순서는 질문별로 회전한다.

시간은 동기 `RAGRetriever.retrieve`의 벽시계 시간이다. 태스크 디스패치·생성 LLM 준비·답변 생성은 포함하지 않으며, 기존 생성 파일럿의 `retrievalMS`와 그대로 합쳐 평균 내지 않는다. 3회의 시간 반복을 서로 다른 법률 질문으로 세지 않고 검색 품질은 질문당 1회만 집계한다. 생성하지 않았으므로 상위 2개 참고 후보의 비관련 비율을 ‘실제 LLM 입력 오염률’로 부르지 않는다.

실제 36회 native 검색의 [방법·품질·시간·결론](retrieval-ablation-2026-11-03/README.md)을 보존했다. 이번 세 질문에서 B1/S/H의 문서 품질 지표는 같았고, 문서 벡터를 재사용해도 B1의 관측 시간이 가장 짧았다. 이는 작은 시뮬레이터 파일럿의 결과이며 전체 법률 질의·실기기로 일반화하지 않는다.

### 장문 판례 요약 평가

장문 요약에서는 다른 판례의 관련성 대신 **현재 판례의 핵심 정보가 입력과 출력에 얼마나 남는지**를 구분한다. [평가 방법과 사전 고정 정답](long-summary-evaluation-2026-11-03/README.md)은 기존 세 원문을 사용한다.

실제 12회 생성의 [결과·네 종류 그래프·오류 사례](long-summary-evaluation-2026-11-03/RESULTS.md)를 별도로 보존했다. H의 숫자상 포함률이 높았던 판례 C에서 K/H의 실제 프롬프트가 같아 검색 이득이라고 해석하지 않는다.

- F는 기존 파서의 구조화 필드를 기존 요약 템플릿·예산에 넣는 기준 조건이다. 외부 참고·UI 후처리를 제외하므로 전체 앱 카드 품질과 동일한 측정은 아니다.
- K/S/H는 `RAGRetriever.retrieveWithin`으로 같은 판례 내부의 쟁점·이유·주문 관점 근거를 선택한다. 기존 참고 검색의 자기 문서 제외 규칙을 우회하지 않고 별도 명시적 진입점을 사용하며, 순위 계산은 공유한다.
- 기존 `retrieve`는 자기 문서 제외·문서당 최대 2청크를 그대로 유지한다. 내부 검색만 단일 문서에서 요청한 topK까지 허용한다. 앱 기본 요약·검색 화면은 내부 검색으로 자동 전환하지 않는다.
- 네 조건은 동일한 생성기·템플릿·예산을 사용한다. 항목별 원문 대조 AI 예비검수와 문장/줄 단위 근거성을 공개하며, 전문가 법률 정확도로 표시하지 않는다.
- [실제 모델 검사](../../code/ios/AISYSAppTests/LongSummaryEvaluationTests.swift)는 원시 입력·출력·검색 결과·시간을 개별 체크포인트로 보존한다. 느린 실제 생성 검사이며, 빠른 회귀 검사와 분리해 실행한다.

#### 문자 제한·생성 변동 분리 실험

[판례 C 통제 실험의 최초 계획](long-summary-controlled-2026-11-04/README.md)은
40회였으나 사용자 요청으로 [24회 균형 설계로 축소](long-summary-controlled-2026-11-04/AMENDMENT.md)했다.
최종 범위는 기존 문자 제한/필드 전체 × F/K/S/H × greedy 2회·고정 seed 42 한 번이다.
같은 검색 선택을 재사용하고 양쪽 모두 평가 전용 8,192 컨텍스트·128 출력 토큰을 사용한다.
실제 입력 사전 검증 결과는 272–1,311토큰이며, 확대 컨텍스트에서도 넘치는 입력은
오류로 거절한다. 전체 프롬프트나 토큰을 조용히 잘라내지 않는다.

`LlamaCppEngine`의 `evaluationContextTokens`와 `generateForEvaluation`은 명시적 평가
진입점이다. 기본 생성 API와 기기별 컨텍스트·자동 seed 정책은 그대로 유지한다.
`LLMPromptTemplate.summarize`도 기본 96자를 유지하며 평가에서만 `fieldLimit: nil`을 전달한다.
각 요청의 실제 입력/출력 토큰·실제 sampler seed·종료 이유를 보존한다.
Greedy 두 회는 재현성 진단으로, seed 42 한 회는 동일 seed의 정책별 비교로 분리한다.
단일 seed이므로 seed 간 평균·표준편차·생성 변동을 평가했다고 쓰지 않는다.
실제 전달 프롬프트가 같은 구성은 별도 그룹으로 표시하고 검색 효과로 해석하지 않는다.
필드 전체 사용은 파서/선택 청크 전체이며 판례 전문 전체를 자동 투입하는 의미가 아니다.
[24개 완료 출력의 결과와 다섯 시각화](long-summary-controlled-2026-11-04/RESULTS.md)를 보존했다.
greedy는 8/8쌍 재현됐지만 문자 제한 해제의 출력 점수 변화는 디코더에 따라 일관되지 않았다.
입력 손실 감소를 실용적인 법률 요약 품질 향상으로 동일시하지 않는다.

## 3. 앱에서 실행

1. 판례 상세 → **원문 근거 분석 · RAG**.

6. **논문용 RAG 평가**에서 합성 자료 또는 자체 평가셋을 불러온다.
7. 실기기에서 반복 횟수를 정하고 3가지 방식을 실행한다. 시뮬레이터에서는 성능 배치 버튼이 제공되지 않는다.
8. 생성 원자료를 검수하고 원자료와 집계를 함께 JSON으로 내보낸다.

내보내기에는 평가셋 본문·원문 발췌가 포함된다. 앱은 자동 전송하지 않는다. 개인정보, 비공개 사건, 이용권한을 확인하고 비식별화한 자료만 공유한다.

## 4. 다섯 지표의 정의

| 항목 | 정의·분모 | 해석 주의 |
| --- | --- | --- |
| 검색 관련성 | 문서 ID 중복 제거 후 상위 3건. P@3 = 정답 문서 수 / 3, R@3 = 정답 문서 수 / 전체 관련 문서 수, MRR@3 = 첫 정답 순위의 역수 | 반환이 1건이어도 P@3 분모는 3. 정답 집합이 비면 Recall/MRR는 미측정이며 별도 무관련 정답 여부를 기록 |
| 생성 근거성 | 인용 ID 존재, 근거 밖 숫자, 따옴표 문구 포함, 정규화 문자 bigram 겹침; 사람 검수 지지 문장 / 검수 문장 | 자동 검사는 표면적 proxy. 사람 검수 결과와 미검수 비율을 별도 보고 |
| 추론 시간 | 실제 primary generate 호출의 시간 합계; 실패 시도 포함 | 모델 로드·복구는 제외. 모델 준비/검색/전체 시간은 별도 필드. 캐시 우회 |
| 메모리 | `task_info(TASK_VM_INFO).phys_footprint`를 50ms 간격으로 표본 수집; 시작/끝/표본 최대 MB 기록 | 앱 전체 프로세스이며 모델 전용 메모리나 절대 피크가 아님. 샘플러는 MainActor에서 재개하므로 긴 동기 구간의 피크를 놓칠 수 있음. 오류는 미측정으로 처리 |
| 출력 성공 | 비어 있지 않고 모든 줄이 인용 형식이며 알려진 근거 ID만 사용한 실행 / 전체 실행 | 법률 정답률·근거성 통과율과 다름. 예산 실패·파싱 실패·모델 실패는 분모에 포함 |

집계의 생성 시간 p50/p95와 최대 메모리는 **실기기이며 요청/실제 검색 모드가 일치한 실행**만 사용한다. 백분위는 nearest-rank 방식이다. 하이브리드 요청이 임베딩 부재로 키워드가 된 경우 하이브리드 검색·근거성 평균에 포함하지 않는다. 출력 성공률은 요청한 실행 전체를 분모로 유지한다. 원자료에는 경고, 의미 점수를 얻은 청크 수와 실제 모드가 남는다.

근거성 자동 평균은 파싱 가능한 출력에서만 계산되므로 반드시 출력 성공률과 함께 보고한다. 사람 검수는 검수된 실행 수와 전체 실행 수도 함께 보고한다. 실패를 제외한 정답률만 단독 보고하지 않는다.

### LLM 출력 품질과 비교 대상

시뮬레이터에서도 실제 출력과 독립 정답·검수를 대조하는 품질 평가는 가능하다. 다만 현재 평가셋의 정답은 관련 문서 ID이며, 모범 답변이나 법률 정답률 채점 기능은 아니다. 실제 GGUF E2E 통과도 인용 형식·연결 확인이지 답변 의미의 정답 판정이 아니다.

주 비교는 같은 **Llama-3.2-1B-Instruct Q4_K_M**에 대해 B0(현재 판례 E0만), B1(키워드 RAG), H(키워드 + **multilingual-e5-base Q8_0**, RRF)를 적용하는 구성 비교다. H는 제안 방식이며 **품질 우승은 아직 미확정**이다. 서로 다른 LLM의 비교나 세계 최고 RAG 선정 실험으로 표현하지 않는다.

실제 답변 정답·필수 조건·예외·근거 구간을 독립적으로 마련하고, 실패를 포함한 품질 지표와 블라인드 검수를 추가해야 한다. 평가 범위, 정확한 모델명, 후속 대조군 및 최고 성능 판정 조건은 [분석 보고서 11절](Execution_Log_Performance_Analysis_2026-11-03.md)에 정리했다. 새 모델과 Ragas·ARES는 미도입 후보이며 실험 결과가 아니다.

## 5. 실제 평가셋 준비

앱에서 합성 평가셋 JSON을 내보내면 가져오기 양식으로 사용할 수 있다.

필수 필드:

- `schemaVersion`: 1.
- `id`: 평가셋 버전 식별자.
- `kind`: `synthetic` 또는 `real`.
- `provenance`: 출처·수집 조건·이용권한 설명.
- `annotator`: 검색 정답 주석 담당자/절차의 식별자.
- `documents`: 고유 `id`, `caseNumber`, `title`, `subject`, `text`, `sourceKind`; 선택 `sourceURL`, `extractedCase`.
- `queries`: 고유 `id`, `targetDocumentID`, `question`, `relevantDocumentIDs`.

중복 ID, 빈 원문/질문, 없는 문서 참조, 자기 자신을 관련 정답에 포함한 데이터는 거절한다. 출처와 검수자 필드는 사용자의 선언이며 앱이 그 진위를 인증하지 않는다.

실제 자료 구성 권장:

1. 이용 가능한 판례를 쟁점별로 구성하고 중복 사건을 합친다.
2. 질문은 생성 모델 출력과 독립적으로 작성한다.
3. 관련 문서는 최소 2인의 법률 검수자가 블라인드 주석하고 불일치를 조정한다.
4. 무관련 질문, 반대 결론, 구별 사유, OCR 오탈자, 긴 판결문을 포함한다.
5. 파라미터를 정하는 개발 자료와 최종 보고용 테스트 자료를 분리한다. 정답을 보고 임계치를 조정한 결과를 최종 평가로 보고하지 않는다.
6. 동일 평가셋을 모든 모드에서 사용하고 평가 후 수정하면 버전을 변경한다.

합성 8문서/3질문은 파일·지표·순위 파이프라인 점검 규모다. 실제 평가셋 크기·쟁점 분포·정답 주석이 없는 상태에서 연구 정확도 수치를 만들지 않는다.

## 6. 실기기 실험 절차

- 기종, OS, 앱 커밋/빌드, GGUF 파일명·SHA-256, 라이브러리 버전, 평가셋 버전을 기록한다.
- 기존 카드 요약과 모델 로딩이 끝난 뒤 시작하고 다른 화면의 추론과 겹치지 않게 한다.
- 전원 연결 여부, 저전력 모드, 주변 온도, 발열 상태, 다른 앱 상태를 통제한다.
- 콜드 로드와 워밍된 모델을 분리한다. 실행별 `modelWasReady`와 모델 준비 시간을 사용하고 서로 섞어 단일 지연으로 보고하지 않는다.
- 최소 반복 수를 실험 전에 정한다. 반복에 따라 모드 시작 순서를 회전하며 개별 실행을 보존한다.
- 정답 주석·검수자 정보를 고정하고 모델 응답 검수 시 검색 방식과 기기 정보를 가린다.
- p50/p95, 실패 수, 임베딩 사용 가능 수, 검수 커버리지, 모델별 표본 수를 함께 보고한다.
- 모델 해시가 미측정이거나 실제 모드가 일치하지 않는 표본을 감추지 않는다.
- 검색 시간에는 임베딩 모델의 최초 로드·해시 확인과 벡터 계산이 포함될 수 있다. 임베딩 cold/warm 및 캐시 상태별로 분리하고 단일 수치로 섞지 않는다.
- 동일 프로세스에서는 임베딩 모델이 검색 후에도 남는다. 모드별 독립 메모리 비교는 앱을 새로 실행한 별도 세션에서 수행하고 공유 모델이 상주한 배치의 프로세스 메모리를 모델 단독 메모리로 해석하지 않는다.
  평가 화면에서 모드 하나만 선택할 수 있다. 개발·회귀 점검에는 기본 3모드 배치를 사용하고 독립 메모리 비교에는 단일 모드/새 앱 세션을 사용한다.
- 이 앱의 표본 메모리에 더해 정확한 메모리 추세가 필요하면 실기기 Instruments 결과를 별도 수집한다.

앱 배치는 모델 생성 실패가 발생한 실행도 남기고 다음 실행을 진행한다. 사용자가 중단하면 미완료 배치를 완성된 평가로 내보내지 않는다. 파일 접근/해시 오류가 나면 오류를 표시한다. 개별 표본에는 출력 성공 여부, 기초 근거 검사율, 출력 SHA-256을 함께 내보내 사람 검수와 원시 응답을 연결한다.

JSON에서 생략된 optional 값은 미측정/해당 없음이며 0점이나 0ms가 아니다. 요청 모드와 실제 모드, 경고, 실패 사유를 항상 함께 확인한다.

## 7. 남은 외부 입력

구현과 기능 테스트만으로 대체할 수 없는 자료:

1. 이용권한이 확인된 실제 판례 원문과 질문·관련 문서 정답.
2. 법률 검수자의 문장별 근거 지지 판정과 검수 절차.
3. 대상 iPhone에서 수행한 반복 실행 및 환경 기록.
4. OCR 정확도를 논문의 별도 결과로 제시하려면 원본 이미지와 사람이 작성한 정답 전사. 현재 평가기는 OCR CER을 계산하지 않는다.

이 자료가 준비되기 전에는 시스템 설계·구현과 기능 검증을 기술할 수 있지만, 실제 법률 정확도나 실기기 성능 향상을 입증했다고 쓰면 안 된다.

## 8. 현재 기능 검증 기록

기존 실행 로그의 시간·실패·버퍼 선언을 pandas로 집계한 별도 [성능·안정성 분석 보고서](Execution_Log_Performance_Analysis_2026-11-03.md)와 그래프를 추가했다. 시뮬레이터 XCTest 시간 분석이며 아래 실기기 실험을 대체하지 않는다.

Xcode 26.1.1 / iOS 26.1 시뮬레이터에서 다음을 확인했다. 아래 테스트 수는 연구 표본 수나 정확도 분모가 아니다.

- 최신 회귀 배치: 기존 14개 + 연구 17개 + 실제 임베딩 5개, 총 **36개 통과**.
- 실제 E5 검색 → 번들 GGUF 생성 → 인용 출력 검사: 별도 **1개 통과**. 가상 표식 문서로 실제 하이브리드 사용, 규칙 기반 fallback 미사용, 생성 실패 없음, 인용 형식과 실제 전달 근거를 검사했다.
- 앞서 통과한 실제 생성 토크나이저·연속 추론 1개까지 포함하면 서로 다른 **38개 테스트**를 실행했다. 동일한 한 배치에서 38개를 실행했다는 뜻은 아니다.
- 한국어 유사 문서/무관 문서 순위, 원문 범위 보존, 중복·사건번호, 수정 후 캐시 무효화, 모델 해시 거절, 역할별 모델 선택, 실패·중단·복구, 지표와 JSON을 검사했다.
- LlamaSwift는 실제 검증에 사용한 revision으로 고정했다. 모델 fetch 스크립트의 SHA 확인과 재실행, 변경 문서 lint 및 패치 공백 검사도 통과했다.

검사 소스는 [기존 회귀](../../code/ios/AISYSAppTests/AISYSAppTests.swift), [연구 경로](../../code/ios/AISYSAppTests/RAGResearchTests.swift), [실제 임베딩·생성](../../code/ios/AISYSAppTests/GGUFEmbeddingTests.swift)에 있다.

이 결과는 **구현의 기능 검증**이다. 실제 법률 정답률, 검색 개선 효과, 4GB iPhone의 메모리·발열·지연은 아직 측정하지 않았으며 논문 실험 결과로 대체할 수 없다.
