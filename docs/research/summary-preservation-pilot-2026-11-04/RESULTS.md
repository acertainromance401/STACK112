# 문장·역할 보존 개선안: 3회 실제 생성 결과

## 1. 결론

**평가용 개선 경로를 구현하고 판례 C에서 K·E5 단독 S·하이브리드 H를 각 한 번 실제 실행했다.
그러나 이번 변경으로 요약 품질이 개선됐다고 판단할 수 없다.**

- 세 구성 모두 제목·참조판례 목록 대신 완결 문장과 파기환송 주문을 입력했다.
- H는 앞 문장 복원으로 실질적 면접교섭권 제한과 제64조 범위 초과를 연결했다.
- 하지만 K는 빈 표제만 출력했고, S/H는 128토큰 상한에서 문장이 잘렸다.
- 출력 핵심 포함률은 K 0.0%, S 0.0%, H 8.3%다. 기존 uncapped seed 42 대비 K는 하락, S/H는 같은 점수다.
- 주문을 입력에 명시했지만 최종 출력의 파기환송 보존은 **0/3**이었다.
- 앱 기본 검색·요약 경로는 변경하지 않았다. 이 결과는 배포 품질 합격이 아니라 실패를 포함한 소규모 개발 관측이다.

점수는 기존 C1–C6 기준의 원문 대조 AI 예비검수이며 법률 전문가 정확도가 아니다.
이미 관찰했던 판례 한 건·seed 하나이므로 독립 평가·통계적 유의성·일반적인 모델 순위를 주장하지 않는다.

## 2. 어떤 문제 때문에 무엇을 바꿨는가

| 기존 문제 | 이번 구현 | 실제 확인한 효과와 남은 한계 |
| --- | --- | --- |
| 쟁점 필드에 제목·사건번호·인용목록이 선택됨 | 최종 근거 선택을 판결요지/결정요지·이유·주문 영역으로 제한 | 최종 근거의 인용목록 편중은 제거. 검색 자체는 기존 320자 청크를 그대로 사용 |
| 청크 시작·96자 재발췌에서 조건·부정이 잘림 | 검색 청크와 겹치는 완결 문장을 원문 위치에서 복원하고 문자 재절단하지 않음 | 모든 전달 근거의 원문 UTF-16 위치 일치. 이것만으로 여섯 핵심 항목을 모두 확보하지는 못함 |
| 비슷한 근거가 필드마다 반복됨 | 법리·사실·판단을 별도 질문으로 검색하고 동일 핵심 문장을 재사용하지 않음 | 역할별 질문만으로 실제 의미 역할은 보장되지 않음. H는 문맥 확장 후 사실 슬롯과 일부 중복 |
| “따라서” 앞의 이유가 누락됨 | 판단 문장이 연결어로 시작하면 바로 앞 원문 문장도 복원 | H에서 이유와 결론 연결 성공. 그러나 출력에는 이 정보가 남지 않음 |
| 파기환송이 입력에서 빠짐 | 한 문장 주문을 구조에서 직접 확보 | 입력 3/3 보존, 출력 0/3. 주문 확보와 생성 보존이 별개임을 확인 |
| 생성기가 사건번호 반복·근거 복사에 치우침 | 법리·사실·판단·주문 네 항목과 부정·조건 보존을 지시 | K는 빈 표제, S/H는 긴 문구 복사. 지시만으로 정보 보존 개선에 실패 |

구현은 [SummaryEvidencePlanner](../../../code/ios/AISYSApp/Sources/SummaryEvidencePlanner.swift),
실제 수집은 [SummaryPreservationEvaluationTests](../../../code/ios/AISYSAppTests/SummaryPreservationEvaluationTests.swift)에 있다.
새 평가 경로만 추가했고 기존 RAG 검색기·E5 모델·RRF 가중치·임계값·운영 프롬프트는 수정하지 않았다.

**이번에는 E5 자체를 재학습하거나 문장별로 재임베딩하지 않았다.**
기존 키워드·E5·RRF의 전체 청크 순위를 재사용하고, 그 순위로 역할 영역의 완결 문장을 선택했다.
따라서 “E5 의미 추출 능력을 강화했다”기보다 **검색 결과의 근거 구성·문맥·입력 방식을 개선한 시도**다.

**개별 변경의 효과를 분리한 ablation이 아니며, 실제 입력 길이도 다르다.**
새 출력 형식은 기존 네 필드 파서와 다르므로 기존 파서 통과율과 직접 비교하지 않는다.

사전 범위는 [README](README.md), 원문·전체 검색·실제 사용자 프롬프트·래핑 프롬프트는
[native manifest](raw/manifest.json)에 보존했다. 정답 항목은 검색기·생성기에 전달하지 않았다.

## 4. 입력·출력 핵심 포함률

full=1, partial=0.5, absent/contradicted=0, 여섯 항목 합계를 6으로 나눈다.

| 구성 | 입력: 기존 제한 / 기존 uncapped / 새 경로 | 출력: 기존 제한 / 기존 uncapped / 새 경로 |
| --- | --- | --- |
| K | 16.7% / 50.0% / **50.0%** | 0.0% / 8.3% / **0.0%** |
| S · E5 단독 | 8.3% / 33.3% / **16.7%** | 0.0% / 0.0% / **0.0%** |
| H | 16.7% / 50.0% / **50.0%** | 0.0% / 8.3% / **8.3%** |

- **K 입력:** C2 권리·집행권원 효력, C3 별도 절차, C6 파기환송을 완전 보존했다. 출력은 모두 누락했다.
- **S 입력:** C6만 완전 보존했다. 법리 문장은 의미적으로 관련되지만 C1–C5의 구체적 평가 관계를 충족하지 못했다.
  특히 “사실”에 절차 위헌 판단, “판단”에 파기환송 결론을 선택해 역할이 어긋났다.
- **H 입력:** C2·C5·C6을 완전 보존했다. 출력은 C2의 일부 미이행 의무 설명만 부분 보존했다.
- H의 기존 uncapped 8.3%는 C5 부분 보존, 이번 8.3%는 C2 부분 보존이다.
  **점수가 같아도 출력 내용과 보존 항목이 같은 것은 아니다.**
- 새 출력의 완전 보존 항목은 0/18, 주문 완전 보존은 0/3이다.

세 새 프롬프트는 서로 다르다. 이번에는 K/H가 같은 입력이었던 이전 조건과 달리 입력 차이는 생겼지만,
그 차이가 충실한 요약 개선으로 이어졌다는 증거는 얻지 못했다.

## 6. 시간·실행 상태

| 구성 | 기존 uncapped 생성(초) | 새 생성(초) | 새 출력 토큰·종료 |
| --- | ---: | ---: | --- |
| K | 229.80 | 188.63 | 10 · EOG |
| S | 227.31 | 165.83 | 128 · 상한 |
| H | 218.50 | 217.41 | 128 · 상한 |

출력 길이·내용이 다르고 K는 내용 없는 출력이므로, 짧아진 시간을 품질 대비 효율 개선이라고 해석하지 않는다.
새 생성 합계는 **571.875초, 약 9.5분**, 실제 수집 XCTest는 **676.282초, 약 11.3분**이었다.
Xcode 실행 전체 730.889초에는 실행 준비가 추가로 포함된다. 구현·빌드·분석 시간과 구분한다.

실제 생성 모델 로딩은 5.565초, 선택은 K 0.109초·S 96.000초·H 0.074초였다.
H는 이미 캐시된 E5 벡터를 재사용했으므로 이 수치를 H의 독립 검색 속도나 K 대비 우위로 해석하면 안 된다.
생성 시간에는 KV/sampler 초기화·토큰화·prefill·생성이 포함되며 모델 로딩·검색은 별도다.

네 항목 모두 내용이 있는 출력은 0/3이다. 빈 표제·사건번호·미완성 원문 조각을 구분해 검수했으며,
불완전한 출력을 원문 근거성 100% 같은 성공 지표로 바꾸지 않았다.
명시적인 반대 진술을 관찰하지 않았다는 것 역시 법률적 정확성 보장이 아니다.

## 7. 남은 원인과 다음 개선 순서

1. **의미 역할의 적합성이 부족하다.** 완결 문장이어도 사실·법리·판단이 뒤섞인다.
   다음에는 일반적인 이유 영역 전체가 아니라 사안의 개요·인정 사실·법원 판단 등의 하위 구조를 구분해야 한다.
2. **문맥 복원 후 중복이 남는다.** H의 판단 앞 문장이 사실 슬롯과 중복된다.
   확장된 근거 집합에 대해 중복을 다시 제거해야 한다.
3. **생성기는 제공된 내용을 충분히 보존하지 못한다.** 세 입력 모두 주문을 포함했지만 출력에서 빠졌다.
   K의 조기 종료와 S/H의 긴 문구 복사는 출력 상한만으로 모두 설명할 수 없다.
4. **128토큰에서 긴 법률 문구를 복사하면 주문까지 도달하지 못한다.**
   다음 진단에서는 짧은 사건 적용·주문을 먼저 출력하는 지시와 출력 예산을 각각 분리해서 시험할 수 있다.
   더 큰 예산이나 모델 교체의 이득은 이번에 측정하지 않았다.

**운영 판단:** 개선안은 평가용으로만 유지한다. 추가 출력이나 앱 기본값 변경은 수행하지 않았다.

## 8. 검증·재현

- 기존 RAG 20개, 기본 정책 2개, 새 문장 보존 3개: **25개 native 검사 통과**.

- Python 분석 회귀 **36개 통과**. 새 분석기는 여섯 항목 검수·인용·해시·원문 위치·실제 seed·토큰·체크포인트를 확인한다.
