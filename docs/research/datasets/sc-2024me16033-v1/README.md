# 실제 판례 파일럿: 2024므16033, 16040

## 출처와 현재 상태

- 법원·선고일: 대법원 2026. 5. 29.
- 사건: 2024므16033, 16040, 이혼등청구의소·이혼등청구의소.
- 사용자 제공 [공식 판결문](https://lx.scourt.go.kr/search/detail/precedent/0/2026000041679).
- 대조 출처: [대법원 판례속보](https://www.scourt.go.kr/portal/news/NewsViewAction.work?seqnum=11138&gubun=4), [국가법령정보센터](https://www.law.go.kr/precInfoP.do?precSeq=622117).
- 2026-11-03에 사건·선고일과 주요 법리·사실·주문을 대조했다. 사용자가 붙여넣은 원문을 보존했으며 웹 원문과 바이트 단위 동일성을 인증하지는 않았다.
- **실제 판례 1건, 평가 질문 10개와 정답 초안**이다. 이 10문항의 독립 법률 전문가 검수, 실제 LLM 실행 및 품질 채점은 아직 하지 않았다. 같은 원문에 다른 판례 2건을 더한 별도 3질문 실험은 [세 판례 파일럿](../family-law-retrieval-v1/README.md)과 분석 보고서 14절에 있다.

## 파일

| 파일 | 용도 |
| --- | --- |
| [source.txt](source.txt) | 사용자 제공 원문. 요약·교정하지 않고 보존했으며 파일 끝에 줄바꿈을 둔다. |
| [answer_key.json](answer_key.json) | 출처 메타데이터, 질문, 정답 초안, 필수·금지 주장, 원문 인용. 앱에 넣는 프롬프트가 아닌 별도 검수 자료다. |
| [dataset.json](dataset.json) | 원문과 질문을 앱의 `RAGEvaluationDataset` v1 형식으로 직렬화한 가져오기 파일. 정답·금지 주장은 모델 입력에 포함하지 않는다. |

새 앱 번들 기본 자료로 자동 포함하지 않는다. 기존 합성 자료를 유지하며 필요할 때 별도로 가져온다.

## 이 판례에서 점검할 능력

| 질문 | 점검 항목 | 정답 초안의 핵심 |
| --- | --- | --- |
| sc-q01 | 원칙의 강도 | 특별한 사정이 없으면 가급적 대상분할 우선 고려. 언제나 강제 아님 |
| sc-q02 | 특별한 사정 | 당사자 합의·객관적 가치 산정 곤란이라는 예시 |
| sc-q03 | 조건·부정·예외 | 형평을 현저히 해하면 대상분할만 고집하지 말고 혼용 적극 고려 |
| sc-q04 | 수치·현금화 | 143억 원과 약 103억 원의 차이는 약 40억 원. 103억 원 전부가 현금 아님 |
| sc-q05 | 심급·주문 | 재산분할 청구 부분 파기환송. 143억 원 지급 확정 아님 |
| sc-q06 | 회사·주식 수 구별 | 원심의 △△△ 2,160주 중 432주와 이 사건 회사 2,000주는 다름 |
| sc-q07 | 불확실성 | 담보대출 가능 여부가 불분명. 가능·불가능 어느 쪽도 확정하지 않음 |
| sc-q08 | 수량 범위 | 양육비는 사건본인 1인당 월 500만 원 |
| sc-q09 | 미제공 결과 거절 | 환송 후 최종 재산분할금은 이 문서로 알 수 없음 |
| sc-q10 | 미제공 외부 원문 거절 | 참조조문 번호만 있고 조문 전문은 없음 |

정답은 글자 일치가 아니라 의미로 검수한다. 필수 주장이 충족되는지, 금지 주장과 같은 중대 오류가 있는지를 본다. 자동 키워드 채점이나 법률 정확성 판정기를 구현한 것은 아니다.

## 한 사건으로 가능한 것과 불가능한 것

**가능:** 현재 판례의 원문 이해, 예외 보존, 수치·주체·심급 구별, 근거 부족에 대한 응답을 점검하는 소규모 파일럿.

**아직 불가능:** B0/B1/H 참고 검색의 우열, 다양한 법률 쟁점에서의 정답률, 최고 모델 선정, 실기기 속도·메모리 결론.

현재 검색기는 자기 자신과 동일 사건을 참고 후보에서 제외한다. 이 파일의 `relevantDocumentIDs`는 모두 빈 배열이며 **관련 판례 정답이 없다는 검색 실험을 충분히 주석했다는 뜻이 아니다.** 단일 코퍼스에서 참고 문서가 존재하지 않음을 나타내는 형식상 값이다. 원문을 여러 문서로 쪼개 ID만 달리하여 관련 판례 수를 부풀리지 않는다.

따라서 세 모드를 실행해도 H의 실제 모드가 `keyword`가 될 수 있고 같은 E0만 전달될 수 있다. 이를 “하이브리드 성능이 낮다/동일하다”거나 “RAG가 불필요하다”는 결론으로 해석하지 않는다. 우선 `currentOnly` 단일 모드로 출력 품질을 점검한다. 본격적인 참고 검색 비교에는 **별개 사건의 관련·무관련 판례와 독립 관련성 주석**을 추가해야 한다.

이 판례는 가사·이혼 분야다. 앱의 형사·경찰시험 관련 사용 범위까지 대표한다고 보지 않으며 쟁점별 표본도 따로 구성해야 한다.

## 앱 사용과 검수

1. 실제 기기의 **논문용 RAG 평가 → JSON 평가셋 가져오기**에서 [dataset.json](dataset.json)을 불러온다. 기존 UI의 시뮬레이터 성능 배치 제한은 바꾸지 않았다.
2. 우선 **현재 판례만**(`currentOnly`) 단일 모드로 실행하고 JSON을 내보낸다. 반복 배치의 작업은 `analysis`다. `oxDraft` 자동 문항 생성과 혼합 집계하지 않는다.
3. 시뮬레이터에서는 개발용 XCTest/harness 또는 등록한 판례의 개별 원문 근거 분석으로 품질 점검을 할 수 있다. 이 데이터만 추가한 상태에서 새 XCTest나 품질 채점기가 자동 실행되지는 않는다.
4. 실행의 `queryID`로 [answer_key.json](answer_key.json)의 같은 ID와 연결한다. 정답 자료를 앱의 판례 코퍼스나 생성 프롬프트에 넣지 않는다.
5. 모드명을 가린 출력에 대해 정답 초안을 독립 검수한 뒤 판정한다. 정확성, 필수 조건 보존, 금지 주장, 근거 지지, 적절한 거절을 별도로 기록한다.
6. 실패·파싱 오류도 전체 요청 분모에 포함하고 검수자·날짜·불일치 조정 절차를 보존한다. 같은 판례의 10문항을 독립 판례 10건이라고 보고하지 않는다.

앱은 전체 원문을 그대로 모델에 넣지 않고 질문 관련 E0 발췌를 선택·축소한다. 정답 초안은 **전체 원문 기준**이며, 실제 전달 발췌에 정답 조건이 남았는지도 별도로 확인해야 한다. 문맥이 빠진 상태에서 올바르게 “근거 부족”이라고 답한 경우 환각으로 취급하지 않되, 전체 원문 과제를 해결한 성공과도 구분한다. 전체 원문에 근거가 없는 sc-q09/q10과 입력 발췌 때문에 일시적으로 답할 수 없는 경우를 혼동하지 않는다.

## 파일 재생성

원문이나 주석을 수정하면 데이터 버전·검수 상태도 갱신한다. 프로젝트 루트에서 기존 `jq`로 앱 입력 파일을 재생성한다.

```bash
cd docs/research/datasets/sc-2024me16033-v1
jq --rawfile text source.txt '{
  schemaVersion: 1,
  id: .datasetID,
  kind: "real",
  provenance: .sourceAudit.scope,
  annotator: (.annotationReview.draftAuthor + ": " + .annotationReview.status),
  documents: [(.document + {text: $text})],
  queries: [.annotations[] | {
    id: .id,
    targetDocumentID: "sc-2024me16033-16040",
    question: .question,
    relevantDocumentIDs: []
  }]
}' answer_key.json > dataset.json
```

평가 설계와 모델 비교는 [온디바이스 RAG 프로토콜](../../OnDevice_RAG_Protocol.md)과 [출력 품질 평가 설명](../../Execution_Log_Performance_Analysis_2026-11-03.md)을 따른다.
